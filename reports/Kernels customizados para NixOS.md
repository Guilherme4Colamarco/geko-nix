# Mantenha o kernel stock e teste CachyOS isolado

Para um desktop NVIDIA + CPU AMD + btrfs, em flake `nixos-unstable` com autoUpgrade que reescreve o `flake.lock`, a recomendação é **manter o kernel stock do nixpkgs (`linux_6_18`, hoje 6.18.55)** e tratar qualquer kernel customizado como experimento isolado em uma `specialisation`. O nixpkgs só mantém dois sabores com patches, `linux_zen` (7.2.9-zen1) e `linux_xanmod` (LTS 6.18.55 e main 7.2.9). O Liquorix saiu, e o CachyOS só chega por flakes de terceiros ([linux-kernels.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/top-level/linux-kernels.nix), [zen-kernels.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/os-specific/linux/kernel/zen-kernels.nix)). O ganho medido é pequeno: cerca de 1% em schedulers sched_ext num jogo limitado por GPU, e pouca diferença entre sabores do CachyOS na maioria das cargas. O custo é real, porque o módulo NVIDIA é recompilado a cada kernel, o cache binário só vale se o `nixpkgs` coincidir com o do fornecedor, e já há um relato de falha de NVIDIA com o kernel do nix-cachyos-kernel. **Duas questões seguem sem resolução nas notas:** se o chaotic-nyx está arquivado e qual o estado real de `linux_lqx`, `linux_hardened` e `linux_rt`. Elas estão marcadas abaixo, junto com o comando `nix eval` para checar localmente. Nada aqui foi medido nesta máquina.

## O nixpkgs só mantém Zen e XanMod; o resto vem de fora

No nixpkgs master de outubro de 2026, o mainline cobre 6.1, 6.6, 6.12, 6.18 e 7.2, mais `linux_testing` (7.3-rc6). `linux_default` aponta para 6.18 e `linux_latest` para 7.2 ([linux-kernels.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/top-level/linux-kernels.nix), [kernels-org.json](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/os-specific/linux/kernel/kernels-org.json)). O `linux_zen` acompanha o latest sem atraso e usa a configuração do linux-zen do Arch: preempção, tick de 1000 Hz, BFQ, futex WAIT_MULTIPLE e NTSYNC. O `linux_xanmod` tem as duas faixas, LTS e main, com BBRv3 e governor performance ([xanmod-kernels.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/os-specific/linux/kernel/xanmod-kernels.nix)). Nenhum dos dois oferece escolha de scheduler. A máquina já roda 6.18.55, igual ao `linux_6_18` do master, então hoje o kernel stock é também o LTS.

O CachyOS é o único caminho para BORE, EEVDF ajustado, BMQ, RT-BORE, variantes `server` e `deckify`, ThinLTO via Clang, níveis x86-64-v2/v3/v4 e `znver4`. Ele chega por dois flakes. O **xddxdd/nix-cachyos-kernel** teve push em 2026-10-07, sincroniza diariamente com o CachyOS por GitHub Action e roda Hydra CI. O **chaotic-cx/nyx** define 11 variantes, com versões vindas de `manifest.json` e `manifest-lts.json` ([README do nix-cachyos-kernel](https://raw.githubusercontent.com/xddxdd/nix-cachyos-kernel/master/README.md), [pkgs/linux-cachyos](https://raw.githubusercontent.com/chaotic-cx/nyx/main/pkgs/linux-cachyos/default.nix)). As versões exatas que o CachyOS entrega hoje não foram lidas. Pelo padrão do projeto, `latest` deve estar em 7.2.x, `lts` em 6.18.x e `rc` em 7.3-rcN, mas isso é inferência.

### Pontos não resolvidos nas notas

**chaotic-nyx: arquivado ou ativo?** As notas se contradizem e esta síntese não escolhe um lado. Uma nota consultou a API do GitHub e registra `archived: false`, com último push em 2026-10-08 e um README que diz "WE'RE BACK FROM THE DEAD!" ([API GitHub](https://api.github.com/repos/chaotic-cx/nyx), [repositório](https://github.com/chaotic-cx/nyx)). Outra nota afirma que o projeto foi arquivado em 2025-12-08 e que o nix-cachyos-kernel virou o caminho principal. Essa afirmação veio de um snippet de busca que não foi confirmado na página ([Discourse](https://discourse.nixos.org/t/packaging-cachyos-in-nixpkgs/75521)). Uma hipótese que concilia os dois dados é que o repositório foi arquivado e depois reaberto, mas nenhuma nota confirma isso. Para decidir, rode `gh api repos/chaotic-cx/nyx --jq '{archived, pushed_at}'` ou `curl -s https://api.github.com/repos/chaotic-cx/nyx | grep -E '"(archived|pushed_at)"'`. De qualquer forma, um histórico de "morreu e voltou" é risco para quem deixa o autoUpgrade puxar o input.

**linux_lqx, linux_hardened, linux_rt.** O estado também é contraditório. Quanto ao Liquorix, uma nota diz que `linux_lqx` foi removido do master com `throw`, por falta de manutenção. A wiki do NixOS ainda lista `linuxPackages_lqx` ([NixOS Wiki](https://wiki.nixos.org/wiki/Linux_kernel)). Pode ser só wiki desatualizada, mas é conflito não resolvido. Quanto ao Hardened, o resumo do `linux-kernels.nix` listou `linux_hardened` e várias `linux_X_hardened` como removidos e, na mesma leitura, disse que `linux_hardened` só contém o latest stable e o latest LTS. Quanto ao RT, as notas só confirmam a remoção de `rt_5_4` até `rt_6_6`; ninguém verificou se `rt_6_12` ou `rt_6_18` existem. PREEMPT_RT está no mainline desde o 6.12, então `structuredExtraConfig` sobre `linux_6_x` seria a alternativa, mas isso não foi verificado no nixpkgs. Como as leituras vieram por resumo de modelo pequeno, trate tudo como não confirmado e cheque no seu `flake.lock`:

```
nix eval --raw nixpkgs#linuxPackages_lqx.kernel.version
nix eval --raw nixpkgs#linuxPackages_hardened.kernel.version
nix eval --raw nixpkgs#linuxPackages_rt.kernel.version
nix eval --raw nixpkgs#linuxPackages_zen.kernel.version
nix eval --raw nixpkgs#linuxPackages_xanmod.kernel.version
nix eval --raw nixpkgs#linuxPackages.nvidiaPackages.stable.version
```

Um atributo removido falha com mensagem `throw`, o que já responde a pergunta. Em flake, `nixpkgs#` usa o registry; para avaliar o nixpkgs travado no repositório, use `.#nixosConfigurations.nixos.pkgs.linuxPackages_lqx.kernel.version`.

## Configurar no flake é simples; o cache é a parte frágil

Com os kernels do nixpkgs basta `boot.kernelPackages = pkgs.linuxPackages_zen;` (ou `_xanmod`, `_latest`). Módulos externos devem sempre sair de `config.boot.kernelPackages`, para casar versão ([NixOS Wiki](https://wiki.nixos.org/wiki/Linux_kernel)). O Hydra nem sempre constrói zen e xanmod. Se faltar cache para a revisão travada, o kernel compila localmente, mas isso não foi verificado contra o Hydra.

Para o nix-cachyos-kernel, o input é `github:xddxdd/nix-cachyos-kernel/release`, **sem `follows` para o nixpkgs**, para não descasar patches e binários. O overlay `pinned` é o recomendado: usa o nixpkgs exato do flake e garante acerto de cache, enquanto o `default` usa o seu nixpkgs e pode causar miss. O atributo fica em `pkgs.cachyosKernels.linuxPackages-cachyos-{latest,lts,bore,...}[-lto][-cpu]` ([README](https://github.com/xddxdd/nix-cachyos-kernel)):

```nix
nixpkgs.overlays = [ inputs.nix-cachyos-kernel.overlays.pinned ];
boot.kernelPackages = pkgs.cachyosKernels.linuxPackages-cachyos-lts;
nix.settings.substituters = [ "https://attic.xuyh0120.win/lantian" ];
nix.settings.trusted-public-keys = [ "lantian:EeAUQ+W+6r7EtwnmYjeVwx5kOGEBpjlBfPlzGlTNvHc=" ];
```

O README manda aplicar a configuração do cache com um `switch` antes de ligar o kernel. Variantes LTO menos usadas (`bmq-lto`, `deckify-lto`, `hardened-lto` e outras) não têm binário em cache. Os atributos `overlays.pinned` e o nome do atributo foram confiados ao README, sem conferência no `flake.nix` do projeto. No chaotic-nyx o input é `github:chaotic-cx/nyx/nyxpkgs-unstable`, também sem `follows`, e o módulo `chaotic.nixosModules.default` adiciona o cache `nyx-cache.chaotic.cx` e expõe `pkgs.linuxPackages_cachyos` ([README](https://github.com/chaotic-cx/nyx)). Não combine os dois projetos.

Aqui está o ponto de atrito com este repositório. O flake usa `nixpkgs` próprio em `nixos-unstable`, e o autoUpgrade (04:40, `operation=boot`) reescreve o lock. Com o overlay `pinned`, o kernel é construído com o nixpkgs do input do projeto, mas o módulo NVIDIA vem do **seu** nixpkgs. Essa combinação pode descasar a versão da API do kernel (inferência, não testada). E qualquer mudança que altere a derivação (`follows`, overlay `default`, override de argumentos, outro compilador) muda o hash e causa cache miss. Isso leva a horas de compilação num autoUpgrade sem supervisão, o que não foi medido. Antes de trocar o kernel, rode `nix build --dry-run` no toplevel e confira "will be fetched" contra "will be built".

## NVIDIA em 6.18 é seguro; patchsets e kernels novos são o risco

O nixpkgs já expõe pacotes NVIDIA para `linux_7_0` (open 595.45.04 beta e 610.43.02 latest) e também para `linux_xanmod_stable` ([MyNixOS](https://mynixos.com/nixpkgs/package/linuxKernel.packages.linux_7_0.nvidia_x11_latest_open), [MyNixOS xanmod](https://mynixos.com/nixpkgs/package/linuxKernel.packages.linux_xanmod_stable.nvidia_x11_beta_open)). A NVIDIA corrige builds para kernels novos por point release; o 580.126.18, por exemplo, trouxe correção para o Linux 6.19 ([PCGH](https://www.pcgameshardware.de/Grafikkarten-Grafikkarte-97980/News/Neuer-Linux-Grafiktreiber-von-Nvidia-1507283/)). Para a série 6.18 isso significa que driver e nixpkgs já cobrem o caso, e é o ponto mais seguro da matriz. Não houve fonte sobre quebras específicas de 6.19 ou 7.x com NVIDIA no NixOS, nem sobre o tempo de correção no nixpkgs.

As falhas documentadas estão em kernels com patches. O nvidia-open-dkms 575.57.08 falhou no XanMod 6.15.1 por objtool/RETHUNK ([GitLab XanMod #439](https://gitlab.com/xanmod/linux/-/issues/439)). No NixOS, o módulo já quebrou com o 6.10 por funções implícitas ([Discourse](https://discourse.nixos.org/t/unable-to-build-nix-due-to-nvidia-drivers-due-or-kernel-6-10/49266)). O relato mais relevante para este caso é a **issue #13 do nix-cachyos-kernel**: com o kernel 6.18.0 e o NVIDIA 590.44.01 (`nvidiaPackages.beta`), a sonda falhou ("NVRM: The NVIDIA probe routine was not called") e outro driver assumiu o dispositivo, enquanto a versão do chaotic-nyx funcionou ([Issue #13](https://github.com/xddxdd/nix-cachyos-kernel/issues/13)). A leitura não mostrou resolução. Um relato de Discourse indica que, no Nyx, definir só o pacote de `nvidiaPackages` do próprio kernel evita colisão ([Discourse](https://discourse.nixos.org/t/experimenting-with-cachyos-kernel-on-nixos-via-chaotics-nyx/70041)). O README do nix-cachyos-kernel não trata de NVIDIA.

Em btrfs não há relato de que Zen, XanMod ou CachyOS corrompam o sistema por seus patches, mas isso é ausência de evidência, não evidência de ausência. Os bugs recentes são upstream: o CVE-2026-46251 afeta versões anteriores a 6.18.14, 6.19.4 e 7.0 ([CVE circl](https://cve.circl.lu/cve/CVE-2026-46251)), e exige a flag experimental `EXTENT_TREE_V2`, improvável num btrfs comum. O 6.18.55 está bem acima do corte. A lição é seguir uma série suportada e atualizada, e um fork que atrasa o stable também atrasa correções de btrfs.

## O ganho medido é pequeno e o risco de manutenção é grande

Os números grandes do CachyOS misturam kernel, compilador (`-march`, LTO), bibliotecas, Mesa e governors. A distro ficou 3,5% acima do Ubuntu 26.04 e 4,3% acima do Fedora 44 na média geométrica, mas isso compara sistemas inteiros ([Phoronix](https://www.phoronix.com/review/cachyos-ubuntu-2604-fedora-44/5)). A comparação de sabores do kernel CachyOS, via snippet de busca (a página devolveu 403), mostrou pouca diferença na maioria das cargas ([Phoronix](https://www.phoronix.com/review/cachyos-linux-flavors/5)). Num teste comunitário de sched_ext no Cyberpunk 2077 (Core Ultra 7 270K Plus + RX 9070 XT), `scx_flash` rendeu +1,37%, `scx_lavd` +0,78% e `scx_bpfland` +0,29% sobre o EEVDF ([fórum CachyOS](https://discuss.cachyos.org/t/share-your-benchmarks/122)). É fonte comunitária, com n pequeno e hardware diferente do seu. O `scx_lavd` da Igalia mostrou FPS médio e 1% low melhores ou similares ao EEVDF ([Phoronix](https://phoronix.com/news/LAVD-Scheduler-Linux-Gaming)). Não existe benchmark independente com NVIDIA e CPU AMD comparando nixpkgs, CachyOS e Zen no mesmo userspace. Para jogos limitados pela GPU, o ganho esperado do scheduler fica na ordem de 1% ou ruído.

Dois motivos comuns para trocar de kernel não valem aqui. O **ntsync** está no mainline desde o 6.14 ([Phoronix](https://www.phoronix.com/news/Linux-6.14-NTSYNC-Driver-Ready)) e, no Proton da Valve, o fsync já é tão rápido quanto ele ([GamingOnLinux](https://www.gamingonlinux.com/2025/03/linux-kernel-6-14-out-late-due-to-pure-incompetence-dont-get-too-excited-about-linux-gaming-boosts/page=1/)), então o stock serve. E o **sched_ext** pode ser testado sem trocar de kernel: o módulo `services.scx` do nixpkgs exige kernel >= 6.12 e só inicia se `/sys/kernel/sched_ext` existir ([scx.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/nixos/modules/services/scheduling/scx.nix)). Se o 6.18 do nixpkgs habilita `CONFIG_SCHED_CLASS_EXT` não foi verificado, e vale checar com `zcat /proc/config.gz | grep SCHED_CLASS_EXT`. O anti-cheat do Proton (EAC e BattlEye) roda em user mode ([Boiling Steam](https://boilingsteam.com/anticheat-support/)), então a inferência é que kernel customizado não o afeta, mas não há relato direto. Secure Boot com lanzaboote assina qualquer kernel, mas não há evidência do uso conjunto com cachyos-kernel e NVIDIA, e não foi verificado se esta máquina o usa (`bootctl status`).

Os riscos que sobram são de operação. Um fork depende do mantenedor para acompanhar as séries estáveis, e a latência de patches de segurança, tanto dos forks quanto do nixpkgs, não foi medida. O `autoUpgrade` multiplica o problema, porque um fork lento ou um input sem cache atrasa ou quebra o próximo boot. A falha de build ali só impede a geração nova, e a geração atual segue intacta.

## Como experimentar sem arriscar o desktop

Se ainda assim houver curiosidade, a ordem de preferência é: primeiro o stock 6.18 LTS, com `services.scx` opcional (`scx_lavd` ou `scx_bpfland`); depois `linuxPackages_zen`, que usa o pipeline de módulos do nixpkgs e tem pacote NVIDIA próprio; por fim o nix-cachyos-kernel na faixa **LTS, não latest**, e só se um teste mostrar ganho. O kernel mais novo que o driver validado, como XanMod ou CachyOS `latest`, é o pior casamento com NVIDIA. O rollout deve usar uma `specialisation`, com o kernel alternativo isolado e o padrão intacto (snippet não verificado em fonte primária, testar com `nixos-rebuild build`):

```nix
specialisation.cachyos.configuration = {
  boot.kernelPackages = lib.mkForce pkgs.cachyosKernels.linuxPackages-cachyos-lts;
};
```

Isso inverte a ordem do exemplo das notas, em que o stock era a specialisation, para que o autoUpgrade nunca troque o kernel padrão. Fixe o input do kernel (rev explícita, sem `nix flake update` automático dele), aplique o cache com um `switch` antes, valide com `nixos-rebuild build` e `boot` (não `switch`), mantenha gerações antigas (`boot.loader.systemd-boot.configurationLimit`) e, depois do boot, confira `nvidia-smi` e `dmesg`. Compare o 1% low no MangoHud em 2 ou 3 jogos antes e depois. Se o ganho não aparecer, descarte.

## Conclusão

A pergunta útil não é qual kernel é mais rápido, e sim se o ganho cobre o custo de manter um segundo canal de atualização. Neste repositório o custo tem forma concreta: um `nixpkgs` próprio que o autoUpgrade reescreve, um módulo NVIDIA recompilado a cada kernel e um cache que só acerta quando as revisões coincidem. Já o benefício medido, perto de 1% em GPU-bound, cabe no ruído. O kernel stock 6.18 LTS é hoje a melhor relação risco-benefício, e o sched_ext oferece o único ganho potencial que dispensa trocar de kernel.

Os dois conflitos (chaotic-nyx arquivado ou ativo; `lqx`, `hardened` e `rt` removidos ou não) não mudam essa recomendação, mas mudam qual alternativa é segura se um dia valer a pena testar. Eles se resolvem em minutos com os comandos acima, e a pesquisa deixa duas lacunas que só medição local fecha: o desempenho real nesta máquina e o comportamento do cache após um `nix flake update`.
